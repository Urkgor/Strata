# Qwen3.6-35B-A3B on Strata: the `strata-q35` engine

Strata's own engine (`strata`) is built for one model, Qwen3.8-Flash-Next. **Qwen3.6-35B-A3B** is a different
architecture, so it runs on a second engine, **`strata-q35`** (the `q35/` folder). Back to the [README](../README.md).

## Which engine for which model

| | `strata` | `strata-q35` |
| --- | --- | --- |
| Models | Qwen3.8-Flash-Next (and its Coder, Swift 1.5 and Unsloth versions) | Qwen3.6-35B-A3B; also the other `qwen35moe`, `qwen35` and `qwen3next` GGUFs |
| Architecture | 48 layers, hyper-connections, sparse-attention indexer, PLE table, 512 experts, top-10 | 40 layers (30 Gated DeltaNet + 10 attention), plain residual, dense attention, 256 experts, top-8, one shared expert |
| Files | ISTA-DASLab's GSQ-RCO GGUFs, Unsloth's | any llama.cpp GGUF of the model (Q4_K_M, UD-Q4_K_XL, Q8_0, ...) |
| Written | CUDA / HIP kernels of its own | llama.cpp's `qwen35moe` graph and its CUDA / CPU kernels, through `libllama` |
| Platforms | Windows and Linux, NVIDIA and AMD | Linux (and wherever llama.cpp builds); NVIDIA through CUDA, or CPU only |

`strata-q35` speaks the same `--serve` protocol, so the Strata server, its web app and its OpenAI and Anthropic APIs
run on it unchanged ([run](#run)). It is built from the llama.cpp commit this repository already pins
(`third_party/ggml/VERSION.txt`), because llama.cpp's API changes from week to week.

## What was checked, and what was not

Checked, in this repository's session (CPU only, no GPU, no access to the model's files):

- **The numbers are PyTorch's.** On a 350-thousand-parameter `qwen3_5_moe` with random weights (the real architecture:
  Gated DeltaNet + gated attention + routed and shared experts), converted with llama.cpp's own converter,
  `strata-q35` writes the same greedy tokens as transformers' reference implementation for prompts of 5, 40 and 200
  tokens (24 tokens each), and its logits agree to 5e-3 (F32; the observed differences are about 1e-4).
- **At the real layer shapes** (`tools/q35_tiny_model.py --preset real-shape`: hidden size 2048, head dimension 256 with
  M-RoPE 11/11/10, 16 query and 2 key/value heads, Gated DeltaNet with 16 key and 32 value heads, 512-wide experts with
  top-8 and a shared expert; only 2 layers and 32 experts, 0.3 billion parameters), F32: the same tokens as PyTorch up to the
  model's end token, and logits within 7e-4. Its Q8_0, Q6_K, Q5_K_M, Q4_K_M, IQ4_XS and Q3_K_M versions
  (`llama-quantize`) run on the K-quant and i-quant paths, and their logit errors grow as the bits shrink, as they should;
  random weights say nothing about how well the real model quantizes.
- **The conversation cache** (below), `STOP`, `SAVE`/`RESTORE`, the sampling keys and the error replies, in
  [`tools/test_q35.py`](../tools/test_q35.py): 14 tests, one second.
- **The Strata server on top of it**: the OpenAI chat API (also streaming), the Anthropic API, and a second turn that reuses
  the first one's cache (22 prompt tokens cached) - with that tiny model.

**Not checked**, and not claimed: Qwen3.6-35B-A3B itself (its files could not be downloaded in that session), the
CUDA backend, any speed, a quantized GGUF of the real model, and a build on RHEL 7 ([RHEL7.md](RHEL7.md) says which
parts are the usual steps and which were only read from the sources). The first run on your hardware is the first
measurement: please add it to [COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md).

## Build

```
tools/build_q35.sh                    # CUDA when nvcc is found, else CPU only -> build-q35/strata-q35
tools/build_q35.sh --cuda on --arch "80;86;89" --jobs 8
tools/build_q35.sh --portable         # AVX2 baseline instead of this CPU: the binary runs on other PCs
tools/build_q35.sh --llama-cpp ~/llama.cpp     # a checkout you already have (offline)
```

or by hand: `cmake -S q35 -B build-q35 -DSTRATA_Q35_CUDA=ON && cmake --build build-q35 -j --target strata-q35`.
It needs a C++17 compiler (GCC 9+), CMake 3.14+ (3.18+ with CUDA) and, for the graphics card, the CUDA toolkit. **On RHEL / CentOS 7
see [RHEL7.md](RHEL7.md).** A binary built on a newer system needs that system's C library:
`tools/check_glibc_symbols.sh build-q35/strata-q35` prints what a binary asks for.

## Run

Generate from a prompt:

```
build-q35/strata-q35 --native Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf --chat --system "Be brief." -p "Why is the sky blue?" -n 400
build-q35/strata-q35 --native model.gguf --chat --think off -p "2+2?" --temp 0.7 --top-p 0.8 --top-k 20
build-q35/strata-q35 --native model.gguf --info          # what the file is
```

`--chat` is a convenience for quick tests: the prompt as one ChatML user message, with the thinking block left open
(`--think on`, the default) or closed (`--think off`: it answers at once). The server uses the model's own chat template.

The server (web app, `/v1/chat/completions`, `/v1/messages`) on the same engine:

```
python tools/q35_setup.py --gguf /models/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf --max-context 65536
pack-q35/run-q35.sh                       # then open http://127.0.0.1:8095/
```

[`tools/q35_setup.py`](../tools/q35_setup.py) reads the GGUF, takes the tokenizer and the model's own chat template out
of it, writes `pack-q35/config.json` (with the sampling the model's GGUF recommends, when it carries any) and the run
script. Nothing is downloaded: you bring the GGUF. Keep `127.0.0.1`; before you listen on other addresses, set
`--api-key` (see the README). The server needs Python 3.10 or newer with `jinja2` and `regex` ([RHEL7.md](RHEL7.md)
says how to get that on RHEL 7); the engine alone needs only its binary.

## Memory

The model is **35 billion parameters, 3 billion of them used per word**: the weights are big, the work per word is small.

- **The file** is the main cost. Estimated from the parameter count (35 B x bits per weight; the GGUF's mixed formats
  keep some tensors larger, so check your file): Q8_0 about 35 GiB, Q6_K 27, Q5_K_M 23, Q4_K_M 20, IQ4_XS 17, Q3_K_M 16.
- **The context** (K/V cache) is small, because only 10 of the 40 layers use attention: with f16, 20 KiB per token
  (10 layers x K and V x 2 heads x 256 x 2 bytes): 640 MiB at 32,768 tokens, 2.5 GiB at 131,072, 5 GiB at the model's
  262,144. `--kv q8_0` takes about 0.53 of that (a quantized V cache needs flash attention: if the engine refuses, add `--flash on`).
- **The recurrent state** of the 30 Gated DeltaNet layers does not grow with the context: measured 2.09 MiB per layer on a
  model with the real layer shape, so about 63 MiB per conversation. Each checkpoint of the
  [conversation cache](#the-conversation-cache) is a copy of it in RAM (`--verbose` logs their size).
- **A ceiling for the experts in RAM, from arithmetic and not a measurement:** a word uses 8 of the 256 experts in each of the
  40 layers, 8 x 40 x (3 x 2048 x 512) = 1.0 billion parameters, about 0.6 GB at Q4 (4.85 bits per weight). That is what the
  CPU reads from RAM per word, so RAM bandwidth alone caps writing at about 80 words per second at 50 GB/s. The card's own
  work, and everything the CPU does besides reading, come on top: the real figure is lower and has to be measured.

## Where the model runs

The same idea as `strata`: the dense part (attention, Gated DeltaNet, shared experts, router, output head) and the K/V
cache on the graphics card, the routed experts - most of the bytes, few of the work - in RAM, computed by the CPU.

| Option | Meaning |
| --- | --- |
| *(nothing)* | everything on the card **fitted to the free VRAM** by llama.cpp's own fit: it moves experts to RAM layer by layer until the model and `--max-context` fit (`--fit-margin-mib`, default 1024, is left free) |
| `--cpu-moe` | all routed experts in RAM, the rest on the card |
| `--n-cpu-moe N` | the experts of the first N layers in RAM |
| `--gpu-layers N` | an exact number of layers on the card (turns the fit off) |
| `--threads N` | CPU threads for writing (default: the physical cores), `--threads-batch` for the prompt |
| `--numa distribute\|isolate\|numactl` | multi-socket PCs: spread the threads, or keep them on the node you started on |
| `--split-mode`, `--main-gpu`, `--tensor-split a,b` | several cards |
| `--load auto\|mmap\|mlock\|none\|direct` | how the file is read (`mlock` pins it in RAM; `direct` is O_DIRECT). With the experts in RAM llama.cpp itself logs a hint to use `none`, which reads them into memory of the engine's own instead of mapping the file |
| `--no-op-offload` | by default the card computes the matrix products of the CPU-resident weights for long prompts (llama.cpp copies them over PCIe); this turns it off |

On a PC without a graphics card (or built with `--cuda off`) everything runs on the CPU.

## The conversation cache

A chat sends the whole conversation every time. `strata` keeps the conversation and reads only what is new; so does this
engine, but the Gated DeltaNet layers keep a **running state** that cannot be stepped back one word like an attention
cache can. So the engine keeps the live sequence and a few **checkpoints** of that state:

- the next request **continues** the live sequence when the new prompt starts with it (the usual follow-up);
- it takes a checkpoint right before the last prompt token, and every `--ckpt-every` tokens (default 8192) inside a long prompt;
- a request that **diverges** (the same prompt again, an edited message, a branch) goes back to the newest checkpoint at or
  before the shared part, and reads from there; with no checkpoint it reads everything again;
- `--ckpt-slots N` (default 4) checkpoints are kept, about 63 MiB of RAM each; 0 turns them off.

The engine says how much it reused: `RESUME <n>` before the prompt is read, and the same number in `DONE`. The server's
`cached_tokens` is that number. `ckpt=0` on a request says no later request extends it (no checkpoint taken).

## The protocol

`strata-q35 --serve ...` reads lines on stdin and answers on stdout, as `strata --serve` does (serve/server.py is its client):

| Line in | Lines out |
| --- | --- |
| *(start)* | `INFO key=value ...` (context, kv, vram_free_mib, arch, n_expert, offload, engine) then `READY <context> stop` |
| `GEN <max_new> [key=value ...] <id,id,...>` | `RESUME <n>`, `PP <read> <total> <ms> <tokens/s>` after each prompt chunk, `T <id>` per token (the end token too), `DONE <generated> <prompt> <prompt ms> <decode ms> <stop\|length\|cancel> 0 0 <reused> 0 0 0 0 0.0 <read> 0` |
| `STOP` | ends the running request at the next token or prompt chunk: `DONE ... cancel` |
| `SAVE <file>` / `RESTORE <file>` | `SAVED <tokens> <bytes> <ms>` / `RESTORED ...`, or `SERR <kind> <0\|1> <why>` |
| `LOGITS <id,id,...>` | `LOGITS 8 <id>:<logit> ...`: the 8 best of the last position (for checking against a reference) |
| `QUIT` | exits |

Sampling keys on `GEN`: `temperature` (absent or 0 = greedy), `top_p`, `top_k`, `min_p`, `seed` (0 = random),
`penalty_repeat`, `penalty_freq`, `penalty_present`, `penalty_last_n` (a penalty without a window counts the last 64
tokens), `ckpt`. Keys of the other engine (`cvec`, `pcie_frac`, ...) are skipped. Errors are one line, `ERR <why>`, and
the engine stays in step.

## What `strata` has that this engine does not

| `strata` | here |
| --- | --- |
| The expert cache in VRAM that learns the busiest experts, expert profiles | llama.cpp places whole layers' experts (`--cpu-moe`, `--n-cpu-moe`, the fit); no adaptive cache |
| MTP draft layer and prompt-lookup speculation | not used: for an MoE model with its experts in RAM a batch of guesses touches more experts, and the gain would have to be measured first |
| Images (`--vision`), the control vector, `--batch` slots, KV streaming, layer split pipeline with the CPU pool | not carried over (several cards: `--split-mode`) |
| `VRAM` command (elastic cache) | answers `ERR` |
| Prebuilt engine and `setup.py` | build it ([RHEL7.md](RHEL7.md)); [`tools/q35_setup.py`](../tools/q35_setup.py) writes the server's files |

## Tests

```
python tools/q35_tiny_model.py /tmp/q35-tiny --llama-cpp third_party/llama.cpp-src      # once: needs torch, transformers 5, tokenizers
STRATA_Q35_ENGINE=build-q35/strata-q35 STRATA_Q35_MODEL_DIR=/tmp/q35-tiny python -m unittest tools.test_q35
python -m unittest tools.test_q35_setup                                                  # no engine needed
```

`q35_tiny_model.py` builds the tiny model with transformers, converts it with llama.cpp's `convert_hf_to_gguf.py`, and
writes PyTorch's answers; `test_q35.py` holds the engine to them. When llama.cpp's pin moves
(`third_party/ggml/VERSION.txt`, `q35/CMakeLists.txt`), run them again before anything else.
