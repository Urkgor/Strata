# Qwen3.6-35B-A3B on Strata: the `strata-q35` engine

Strata's own engine (`strata`) is built for one model, Qwen3.8-Flash-Next. **Qwen3.6-35B-A3B** is a different
architecture, so it runs on a second engine, **`strata-q35`** (the `q35/` folder). Back to the [README](../README.md).

## Which engine for which model

| | `strata` | `strata-q35` |
| --- | --- | --- |
| Models | Qwen3.8-Flash-Next (and its Coder, Swift 1.5 and Unsloth versions) | Qwen3.6-35B-A3B (`qwen35moe`); the engine also lets `qwen35` and `qwen3next` GGUFs through, which were not tested |
| Architecture | 48 layers, hyper-connections, sparse-attention indexer, PLE table, 512 experts, top-10 | 40 layers (30 Gated DeltaNet + 10 attention), plain residual, dense attention, 256 experts, top-8, one shared expert |
| Files | ISTA-DASLab's GSQ-RCO GGUFs, Unsloth's | any llama.cpp GGUF of the model (Q4_K_M, UD-Q4_K_XL, Q8_0, ...) |
| Written | CUDA / HIP kernels of its own | llama.cpp's `qwen35moe` graph and its CUDA / CPU kernels, through `libllama` |
| Platforms | Windows and Linux, NVIDIA and AMD | Linux (and wherever llama.cpp builds); NVIDIA through CUDA, or CPU only |

`strata-q35` speaks the same `--serve` protocol, so the Strata server, its web app and its OpenAI and Anthropic APIs
run on it unchanged ([run](#run)). It is built from the llama.cpp commit this repository already pins
(`third_party/ggml/VERSION.txt`), because llama.cpp's API changes from week to week, **plus one patch of ours**
(`q35/patches/`, applied by the build) that adds [the expert cache](#the-expert-cache-what-makes-it-more-than-llamacpp):
without it the engine would be llama.cpp, and run at llama.cpp's speed.

## What was checked, and what was not

Checked, in this repository's session (CPU only, no GPU, no access to the model's files):

- **The numbers are PyTorch's.** On a 350-thousand-parameter `qwen3_5_moe` with random weights (the real architecture:
  Gated DeltaNet + gated attention + routed and shared experts), converted with llama.cpp's own converter,
  `strata-q35` writes the same greedy tokens as transformers' reference implementation for prompts of 5, 40 and 200
  tokens (24 tokens each), and its logits agree to 5e-3 (F32; the observed differences are about 1e-4).
- **At the real layer shapes** (`tools/q35_tiny_model.py --preset real-shape`: hidden size 2048, head dimension 256 with
  M-RoPE 11/11/10, 16 query and 2 key/value heads, Gated DeltaNet with 16 key and 32 value heads, 512-wide experts with
  top-8 and a shared expert; only 2 layers and 32 experts, 0.3 billion parameters), F32: the same tokens as PyTorch up to the
  model's end token, and logits within 7e-4. Its Q8_0, Q6_K, Q5_K_M, Q4_K_M, IQ4_XS and Q3_K_M versions
  (`llama-quantize`) run on the K-quant and i-quant paths, and their logit errors grow as the bits shrink, as they should;
  random weights say nothing about how well the real model quantizes.
- **The conversation cache** (below), `STOP`, `SAVE`/`RESTORE`, the sampling keys and the error replies, in
  [`tools/test_q35.py`](../tools/test_q35.py): 14 tests, one second.
- **The expert cache never changes an answer** (CPU only: the cache can live in RAM, so the graph, the tables, the copies
  from the file and the policy all run as they do with a card). On the tiny model and on the real-layer-shape one, with
  `--no-repack` on both sides (the same kernels): the logits of 40 prompts of 1 to 40 tokens are **identical to the last printed
  digit** with and without the cache (Q8_0, Q6_K and Q4_K_M, caches of 8 and 20 of the 32 experts of each layer), and 30 prompts of
  40 greedy tokens each give the same tokens in 11 of 12 cases (Q8_0, Q6_K, Q5_K_M, Q4_K_M, IQ4_XS and Q3_K_M, caches of 8 and 20 experts):
  in the twelfth (IQ4_XS) one prompt differs after a few tokens, because llama.cpp's CPU kernel for several rows of one expert is a
  different kernel from the one for a single row, and the cache changes how many rows an expert gets. With llama.cpp's weight
  repacking on (the default) the logits of the same prompts differ by at most 2e-3 (Q4_K_M), 2.5e-2 (IQ4_XS) and 0 (Q8_0, Q6_K), where merely
  switching flash attention off moves them by 4.7e-2 to 7.6e-2. These are random weights: the real model's sensitivity is unknown.
- **The cache learns**: in [`tools/test_q35.py`](../tools/test_q35.py) (9 more tests, and 6 for the speculation below: 29 in all, 3 seconds) the hit rate rises over repeated requests, a profile
  warms the next start, and `--bench`, `--sim-cache` and the self-check run. The policy alone has a unit test
  (`q35/test_expert_cache.cpp`) on *synthetic* skewed routing - not the model's: with the experts' popularity skewed like 1/rank^0.9
  it reaches hit rates of 37 / 49 / 60 / 70 / 82 % with 5 / 10 / 18 / 30 / 50 % of the experts of every layer cached, and
  follows a change of topic back to its former rate in a few thousand tokens.
- **The Strata server on top of it**: the OpenAI chat API (also streaming), the Anthropic API, and a second turn that reuses
  the first one's cache (22 prompt tokens cached) - with that tiny model.

**Not checked**, and not claimed: Qwen3.6-35B-A3B itself (its files could not be downloaded in that session), the
CUDA backend - **so the expert cache has run only with its "card" in RAM, and its speed on a real card is unmeasured** - any
speed, a quantized GGUF of the real model, and a build on RHEL 7 ([RHEL7.md](RHEL7.md) says which
parts are the usual steps and which were only read from the sources). The first run on your hardware is the first
measurement: please add it to [COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md).

## Build

```
tools/build_q35.sh                    # CUDA when nvcc is found, else CPU only -> build-q35/strata-q35
tools/build_q35.sh --cuda on --arch "80;86;89" --jobs 8
tools/build_q35.sh --portable         # AVX2 baseline instead of this CPU: the binary runs on other PCs
tools/build_q35.sh --llama-cpp ~/llama.cpp     # a checkout you already have (offline; the build patches it, see below)
```

The build applies `q35/patches/0001-hybrid-expert-cache.patch` to the llama.cpp sources (it needs `patch(1)` or `git`;
`yum install patch` on RHEL 7) and remembers it did (`.strata-patched-*` in that folder). By hand: `cmake -S q35 -B build-q35 -DSTRATA_Q35_CUDA=ON && cmake --build build-q35 -j --target strata-q35`.
It needs a C++17 compiler (GCC 9+), CMake 3.14+ (3.18+ with CUDA) and, for the graphics card, the CUDA toolkit. **On RHEL / CentOS 7
see [RHEL7.md](RHEL7.md).** A binary built on a newer system needs that system's C library:
`tools/check_glibc_symbols.sh build-q35/strata-q35` prints what a binary asks for.

## Run

Generate from a prompt:

```
build-q35/strata-q35 --native Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf --chat --system "Be brief." -p "Why is the sky blue?" -n 400
build-q35/strata-q35 --native model.gguf --chat --think off -p "2+2?" --temp 0.7 --top-p 0.8 --top-k 20
build-q35/strata-q35 --native model.gguf --info          # what the file is
```

`--chat` is a convenience for quick tests: the prompt as one ChatML user message, with the thinking block left open
(`--think on`, the default) or closed (`--think off`: it answers at once). The server uses the model's own chat template.

The server (web app, `/v1/chat/completions`, `/v1/messages`) on the same engine:

```
python tools/q35_setup.py --gguf /models/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf --max-context 65536
pack-q35/run-q35.sh                       # then open http://127.0.0.1:8095/
```

[`tools/q35_setup.py`](../tools/q35_setup.py) reads the GGUF, takes the tokenizer and the model's own chat template out
of it, writes `pack-q35/config.json` (with the sampling the model's GGUF recommends, when it carries any) and the run
script. Nothing is downloaded: you bring the GGUF. Keep `127.0.0.1`; before you listen on other addresses, set
`--api-key` (see the README). The server needs Python 3.8 or newer and no package (no Jinja2, no `regex`: its chat-template renderer and its tokenizer pattern are in the standard library; [RHEL7.md](RHEL7.md) says how to get Python 3.8 on RHEL 7); the engine alone needs only its binary.

## Memory

The model is **35 billion parameters, 3 billion of them used per word**: the weights are big, the work per word is small.

- **The file** is the main cost. Estimated from the parameter count (35 B x bits per weight; the GGUF's mixed formats
  keep some tensors larger, so check your file): Q8_0 about 35 GiB, Q6_K 27, Q5_K_M 23, Q4_K_M 20, IQ4_XS 17, Q3_K_M 16.
- **The context** (K/V cache) is small, because only 10 of the 40 layers use attention: with f16, 20 KiB per token
  (10 layers x K and V x 2 heads x 256 x 2 bytes): 640 MiB at 32,768 tokens, 2.5 GiB at 131,072, 5 GiB at the model's
  262,144. `--kv q8_0` takes about 0.53 of that (a quantized V cache needs flash attention: if the engine refuses, add `--flash on`).
- **The recurrent state** of the 30 Gated DeltaNet layers does not grow with the context: measured 2.09 MiB per layer on a
  model with the real layer shape, so about 63 MiB per conversation. Each checkpoint of the
  [conversation cache](#the-conversation-cache) is a copy of it in RAM (`--verbose` logs their size).
- **A ceiling for the experts in RAM, from arithmetic and not a measurement:** a word uses 8 of the 256 experts in each of the
  40 layers, 8 x 40 x (3 x 2048 x 512) = 1.0 billion parameters, about 0.6 GB at Q4 (4.85 bits per weight). That is what the
  CPU reads from RAM per word, so RAM bandwidth alone caps writing at about 80 words per second at 50 GB/s. The card's own
  work, and everything the CPU does besides reading, come on top: the real figure is lower and has to be measured.

## Where the model runs

The same idea as `strata`: the dense part (attention, Gated DeltaNet, shared experts, router, output head) and the K/V
cache on the graphics card, the routed experts - most of the bytes, few of the work - in RAM, computed by the CPU.

| Option | Meaning |
| --- | --- |
| *(nothing)* | everything on the card **fitted to the free VRAM** by llama.cpp's own fit: it moves experts to RAM layer by layer until the model and `--max-context` fit (`--fit-margin-mib`, default 1024, is left free) |
| `--cpu-moe` | all routed experts in RAM, the rest on the card |
| `--n-cpu-moe N` | the experts of the first N layers in RAM |
| `--gpu-layers N` | an exact number of layers on the card (turns the fit off) |
| `--threads N` | CPU threads for writing (default: the physical cores), `--threads-batch` for the prompt |
| `--poll N` | 0-100: how long idle CPU threads spin before they sleep (default 50, as llama.cpp; 100 spins longer: no gain was measured on the CPU-only test) |
| `--numa distribute\|isolate\|numactl` | multi-socket PCs: spread the threads, or keep them on the node you started on |
| `--split-mode`, `--main-gpu`, `--tensor-split a,b` | several cards |
| `--load auto\|mmap\|mlock\|none\|direct` | how the file is read (`mlock` pins it in RAM; `direct` is O_DIRECT). With the experts in RAM llama.cpp itself logs a hint to use `none`, which reads them into memory of the engine's own instead of mapping the file |
| `--batch N`, `--ubatch N` | prompt batch sizes (default 2048 / 512). With the experts in RAM a larger `--ubatch` (try 2048) can read long prompts faster, because the card is handed the CPU's weights once per micro-batch; not measured here |
| `--no-op-offload` | by default the card computes the matrix products of the CPU-resident weights for long prompts (llama.cpp copies them over PCIe); this turns it off |

On a PC without a graphics card (or built with `--cuda off`) everything runs on the CPU.

**The CPU threads are kept between graphs.** With the experts in RAM a token is some eighty graphs (the card's part, then the
CPU's, layer after layer), and ggml without a thread pool of its own starts a new team of threads for each of them. The first
version of this engine did that; it now keeps one pool, as llama.cpp's own tools do (`--no-threadpool` brings the old behaviour
back, to compare). Measured on a CPU-only run, where a token is a single graph: the real-layer-shape Q4_K_M model (2 layers, 32 experts),
4 threads, 64 tokens a run: 324 to 358 tokens/s without the pool (medians of three runs, four trials), 385 to 399 with it, about 14% more;
`--poll 100` showed no consistent further gain. With a card the graphs are many more, and so should the saving be - not measured.

## The expert cache: what makes it more than llama.cpp

With the experts in RAM, llama.cpp computes every routed expert of a word on the CPU while the card waits: the CPU reads
about 0.6 GB of experts per word at Q4 (see [Memory](#memory)), and the card's memory that is left over sits idle.
That is why a plain `llama.cpp` and the first version of this engine write at the same speed.

`strata` does it differently: all the experts stay in RAM, **the card keeps a cache of the ones the model asks for most**, and
a decode step has the card compute the cached ones while the CPU computes only the rest. This engine does the same, in
llama.cpp's graph:

- the router picks 8 experts per token and layer; a small table per layer says which of the 256 are in the card's cache;
- the cached ones are computed **on the card** (from copies of the file's own bytes), the others **on the CPU**; for each slot exactly
  one of the two results is non-zero, so adding them is exact, and the slots are then summed in llama.cpp's own order:
  the answer is the one without the cache (see [what was checked](#what-was-checked-and-what-was-not));
- after every step the engine reads which experts were used (the graph copies the router's choice into a small tensor)
  and moves the busiest uncached experts into the cache in place of the least used cached ones: counts that halve every
  512 tokens, 2 experts moved per step once the cache is full (24 while it fills; a long prompt fills it at once),
  so the cache follows the conversation;
- batches of up to `--cache-tokens` tokens (16) use it; longer prompts keep llama.cpp's own path, in which the card computes
  the CPU's weights over PCIe;
- at the start the engine **checks on the first tokens that the cache gives the usual answers** (`--cache-check`): on a mismatch
  it switches itself off and says so, so a CUDA problem cannot silently garble an answer.

```
build-q35/strata-q35 --native model.gguf --chat -p "..." --expert-cache auto       # the card's free memory is the cache
build-q35/strata-q35 --native model.gguf --serve --expert-cache 6000               # 6000 MiB of it
```

| Option | Meaning |
| --- | --- |
| `--expert-cache auto` | all routed experts in RAM and the card's free memory (after the model, the K/V cache and the compute buffers, minus `--fit-margin-mib`, default 1024) as the cache. If the whole model fits the card, nothing is moved and there is no cache |
| `--expert-cache MIB` | that much of the card's memory instead |
| `--expert-cache sim` | no cache: only records which experts are used and reports [what caches of several sizes would have given](#measuring-what-the-cache-gives-you) |
| `--cache-slots N` | N experts per layer instead of a size |
| `--cache-profile FILE` | writes what the model asked for (and every 4096 tokens), reads it at start: a warm cache after a restart. `q35_setup.py` sets `pack-q35/hot-experts.bin` |
| `--cache-swaps N`, `--cache-half-life N`, `--cache-tokens N`, `--cache-check on\|off` | the policy and its checks |
| `--cpu-moe`, `--n-cpu-moe N` | as before: the layers whose experts are in RAM are the ones that get a cache |

Written into the INFO line (`expert_slots`, `expert_cache_mib`) and, per request, into DONE (`hits`, `lookups`: the share of
expert uses the card served; the server logs "expert cache X% hit").

What it does **not** do, compared with `strata`: the card and the CPU work **one after the other** within a layer, not at the
same time. llama.cpp's scheduler waits for the card before it hands work to the CPU, and overlapping them needs an engine of
one's own. The cache therefore saves the CPU's share (the card does the cached experts' work in a fraction of the time), but
the two do not overlap. Also: experts with per-expert scales or biases (NVFP4) are not cached, LoRA adapters do not go through
the cache, and several cards were not tried (each card caches its own layers' experts).

**Expected gain, from arithmetic, not from a measurement:** the CPU reads (1 - hit rate) of the 0.6 GB, so at a 70% hit rate the
CPU's part of a step shrinks to about a third, and the card adds a few fractions of a millisecond per layer. How much of the step the
CPU's part is, and what the hit rate of this model's real routing is, depends on your PC and on what you write: measure them (next section).
There is no gain when the whole model already fits the card, and little when the dense part alone leaves no room for a cache.

## Measuring what the cache gives you

```
# 1. what hit rate would a cache of this size have on MY prompts?  (no cache needed: the experts stay where they are)
build-q35/strata-q35 --native model.gguf --cpu-moe --expert-cache sim --sim-cache 5,10,18,30,50 -f my-prompt.txt -n 400
#    -> "a cache of 5% (12 per layer) 10% ... would have served 41.2% 55.0% ... of the expert uses"

# 2. speed: the same prompt and answer with and without the cache, in one run
build-q35/strata-q35 --native model.gguf --expert-cache auto --bench --bench-compare -f my-prompt.txt --bench-pp 512 --bench-tg 128
#    -> bench[cache] 1/3  prompt 512 tokens XX.X tok/s | generation 128 tokens XX.XX tok/s (...) | cache: XX.X% hits, X.XX copies/token, X.XX ms upkeep/token
#       bench[usual] ...
#       bench: with cache generation is X.XXx the speed of the usual graphs (XX.XX vs XX.XX tok/s)
```

`--bench` runs `--bench-reps` times (3): the first run starts with an empty cache, so the later ones show what it gives once warm.
`--bench-compare` runs the same on a fresh context without the cache, which is llama.cpp's own placement and speed.
Numbers from a real card are welcome in [COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md).

## Speculation: `--spec lookup`

`strata` writes several tokens per step when it can guess them (prompt lookup, and the model's own draft layer). This
engine has the first kind, off by default:

```
build-q35/strata-q35 --native model.gguf --serve --spec lookup                 # up to 4 guessed tokens per step
build-q35/strata-q35 --native model.gguf --serve --spec lookup --spec-max 6 --spec-match 3
```

After each token the engine looks in the prompt and in the answer so far for the last `--spec-match` (2) to 4 tokens; if
they occurred before, the tokens that followed are the guess (at most `--spec-max`, 4). The token and the guesses go through the
model **in one batch**, and the model's own rows say which guesses were right: **every token is sampled from the model's
row for that position, in order, and a guess is kept only when the sampler produced exactly it**, so the answer is the one
without guesses, with greedy and with sampled decoding alike (the same seed gives the same tokens). Where a guess was
wrong, the recurrent state steps back through llama.cpp's snapshots of the last `--spec-max` tokens
(`n_rs_seq`) and the attention cache is cut; no checkpoint is read. After a guess nobody believed, the engine stops guessing for a few
tokens (1, 2, 4 ... 16), so text that never repeats costs next to nothing; the snapshots cost some memory (the
checkpoint size did not change) and a little time on every step, which is why it is off by default.

It helps where the text repeats: code and its edits, JSON, quotations, lists, a summary of what is in the prompt. A request may also
carry `spec_hint=<id,id,...>`, tokens the answer is likely to contain (the file being edited, say): they are searched first.
On a batch of several tokens the CPU reads more experts than for one (the union of what the tokens choose), so for this
model with its experts in RAM the gain is smaller than for a dense one and **has to be measured on your text**:
`--bench --bench-compare --spec lookup -f your-text.txt` shows both speeds and how many guesses were right (the bench prompt
and answer are your text's, not a repeating filler: a repeating prompt flatters the guesses). The server shows the
numbers as `draft_n` and `draft_n_accepted`.

Checked here, on CPU: with perfect, partly wrong and late hints, on 30 prompts each of the tiny model, the answers are
token for token the ones without guesses (greedy and seeded sampling); in three runs 77, 79 and 91% of the 466 to 907 guesses were accepted
and the others rolled back. On the quantized real-layer-shape models some prompts diverge after a few tokens: a batch of several tokens and a single
token take different paths in the Gated DeltaNet and in the matrix products, and those random weights amplify float
noise (turning flash attention off alone changes the tokens of 13 prompts in 30). **Not done: the model's own MTP draft layer**,
which `strata` uses: the pinned llama.cpp can run it for a GGUF that carries the layer, but this engine does not drive it yet.

## The conversation cache

A chat sends the whole conversation every time. `strata` keeps the conversation and reads only what is new; so does this
engine, but the Gated DeltaNet layers keep a **running state** that cannot be stepped back one word like an attention
cache can. So the engine keeps the live sequence and a few **checkpoints** of that state:

- the next request **continues** the live sequence when the new prompt starts with it (the usual follow-up);
- it takes a checkpoint right before the last prompt token, and every `--ckpt-every` tokens (default 8192) inside a long prompt;
- a request that **diverges** (the same prompt again, an edited message, a branch) goes back to the newest checkpoint at or
  before the shared part, and reads from there; with no checkpoint it reads everything again;
- `--ckpt-slots N` (default 4) checkpoints are kept, about 63 MiB of RAM each; 0 turns them off.

The engine says how much it reused: `RESUME <n>` before the prompt is read, and the same number in `DONE`. The server's
`cached_tokens` is that number. `ckpt=0` on a request says no later request extends it (no checkpoint taken).

## The protocol

`strata-q35 --serve ...` reads lines on stdin and answers on stdout, as `strata --serve` does (serve/server.py is its client):

| Line in | Lines out |
| --- | --- |
| *(start)* | `INFO key=value ...` (context, kv, vram_free_mib, arch, n_expert, offload, engine) then `READY <context> stop` |
| `GEN <max_new> [key=value ...] <id,id,...>` | `RESUME <n>`, `PP <read> <total> <ms> <tokens/s>` after each prompt chunk, `T <id>` per token (the end token too), `DONE <generated> <prompt> <prompt ms> <decode ms> <stop\|length\|cancel> <guesses right> <guesses> <reused> <hits> <lookups> 0 0 0.0 <read> <experts copied into the cache>` |
| `STOP` | ends the running request at the next token or prompt chunk: `DONE ... cancel` |
| `SAVE <file>` / `RESTORE <file>` | `SAVED <tokens> <bytes> <ms>` / `RESTORED ...`, or `SERR <kind> <0\|1> <why>` |
| `LOGITS <id,id,...>` | `LOGITS 8 <id>:<logit> ...`: the 8 best of the last position (for checking against a reference) |
| `QUIT` | exits |

Sampling keys on `GEN`: `temperature` (absent or 0 = greedy), `top_p`, `top_k`, `min_p`, `seed` (0 = random),
`penalty_repeat`, `penalty_freq`, `penalty_present`, `penalty_last_n` (a penalty without a window counts the last 64
tokens), `ckpt`, `spec_hint` (with `--spec lookup`). Keys of the other engine (`cvec`, `pcie_frac`, ...) are skipped. Errors are one line, `ERR <why>`, and
the engine stays in step.

## What `strata` has that this engine does not

| `strata` | here |
| --- | --- |
| The expert cache in VRAM that learns the busiest experts, expert profiles | [the expert cache](#the-expert-cache-what-makes-it-more-than-llamacpp) and `--cache-profile`: the same idea, on llama.cpp's graph, with the card and the CPU working one after the other (no overlap within a layer) |
| MTP draft layer and prompt-lookup speculation | [prompt lookup](#speculation---spec-lookup), off by default (`--spec lookup`); the MTP draft layer is not driven yet |
| Images (`--vision`), the control vector, `--batch` slots, KV streaming, layer split pipeline with the CPU pool | not carried over (several cards: `--split-mode`) |
| `VRAM` command (elastic cache) | answers `ERR` |
| Prebuilt engine and `setup.py` | build it ([RHEL7.md](RHEL7.md)); [`tools/q35_setup.py`](../tools/q35_setup.py) writes the server's files |

## First run on your machine

Nothing here has run on the real model yet, so the first run is also a check. In this order:

1. `tools/build_q35.sh`, then `tools/check_glibc_symbols.sh build-q35/strata-q35` (RHEL 7: nothing above GLIBC 2.17).
2. `build-q35/strata-q35 --native model.gguf --info` should say `architecture qwen35moe`, 40 layers (hybrid: yes), 256 experts,
   8 per token, a 248,320-token vocabulary.
3. `build-q35/strata-q35 --native model.gguf --chat -p "Say hello in French." -n 60`: a sensible answer, and on stderr the
   placement (`strata-q35: fitted to the free VRAM: ...`) and `prompt N tokens at X tokens/s, answer M tokens at Y tokens/s`.
4. If the answer is garbage, narrow it down by changing one thing at a time: `--gpu-layers 0` (CPU only), `--flash off`,
   `--kv f16`, `--cpu-moe`. A garbled answer on the card that is fine on the CPU is a CUDA-build problem (architecture list,
   toolkit), not a model problem.
5. Send the two numbers of step 3, the card, the CPU, the RAM and the file's name to
   [COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md).

`test_q35.py` also runs the expert cache with the "card" in RAM (`--cache-in-ram`, for PCs without one: its `--bench` numbers say nothing about a card) and the speculation. `q35_tiny_model.py` builds the tiny model with transformers, converts it with llama.cpp's `convert_hf_to_gguf.py`, and
writes PyTorch's answers; `test_q35.py` holds the engine to them. When llama.cpp's pin moves
(`third_party/ggml/VERSION.txt`, `q35/CMakeLists.txt`), run them again before anything else.
